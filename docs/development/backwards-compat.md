# Semantic Compatibility Engineering Policy

RunMat is an independent runtime for MATLAB-language source code. Compatibility work is based on publicly available documentation and independent engineering. This policy explains how the project selects a documented semantic reference, evaluates behavior that has changed across releases, and preserves older source code where practical.

MATLAB is a registered trademark of The MathWorks, Inc. RunMat is not affiliated with or endorsed by The MathWorks, Inc.

## Scope

This policy applies to observable behavior in RunMat-supported surfaces, including:

- language syntax and evaluation semantics;
- values, classes, shapes, indexing, and assignment;
- builtin inputs, outputs, warnings, and errors;
- persistence and documented file-format behavior; and
- CPU and accelerated execution of supported operations.

This policy does not:

- claim complete coverage of the MATLAB language or product family;
- make implementation details of another runtime part of RunMat's contract;
- reproduce product licensing or packaging;
- require RunMat to share another product's performance characteristics, resource limits, or internal architecture; or
- turn undocumented behavior into a compatibility requirement.

Feature support is documented separately. A compatibility target identifies the reference used for matching semantic behavior. It does not imply that every toolbox or feature in that release is implemented, but language behavior will aim to match compatibility with existing code written for that release.

## Current semantic target

The current semantic compatibility target for RunMat is **MATLAB R2026a**.

## Compatibility vocabulary

**Semantic target**: The pinned release whose observable or online documented behavior is the primary reference for supported behavior.

**Legacy compatibility envelope**: Documented behavior from earlier releases that RunMat can preserve without conflicting with the semantic target.

**Conflict**: A case where the same supported program and inputs cannot exhibit both the target behavior and an older behavior.

**RunMat extension**: Deliberate behavior or syntax provided by RunMat that is outside the documented target surface.

**Observable behavior**: A program-visible result such as a value, class, shape, side effect, warning, error, or accepted call form. Internal algorithms and data structures are not observable behavior for this policy.

## Decision order

When implementing or reviewing a supported surface, use this order:

1. Follow behavior explicitly documented for the semantic target.
2. Follow documented target-release errors, warnings, and unsupported cases when they are material to program behavior.
3. Preserve older call forms and behaviors that the target still accepts.
4. Preserve additional documented legacy behavior when it does not conflict with the target.
5. Treat behavior beyond that surface as a RunMat extension only after an explicit engineering decision.
6. When reliable public evidence is insufficient, record the ambiguity and use a safe, deterministic provisional behavior rather than claiming parity.

Current target behavior takes precedence in a genuine conflict. This rule keeps the runtime forward-facing without unnecessarily excluding older source code.

## Backward compatibility policy

RunMat aims to execute existing MATLAB-language source code across a broad compatibility envelope. That aim is applied behavior by behavior rather than by declaring that every script from a particular historical release is supported.

The RunMat project should:

- continue to support an older call form when the semantic target still supports it;
- distinguish "not recommended" from removed or unsupported functionality;
- avoid requiring source rewrites solely to use a newer preferred spelling;
- preserve nonconflicting legacy syntax and semantics when the implementation cost and maintenance burden are reasonable;
- preserve documented interchange formats where the relevant RunMat feature supports them; and
- test legacy behavior that RunMat intentionally retains.

The project is not required to preserve an older behavior when it conflicts with the semantic target. In such a case, the target behavior applies unless the project explicitly adopts a mode-gated RunMat extension.

There is no blanket earliest-supported MATLAB release. A historical behavior is inside the compatibility envelope only when it is supported by adequate public evidence, relevant to a RunMat surface, and not displaced by this policy.

## Compatibility modes

RunMat's `runmat`, `matlab`, and `strict` modes are language-policy modes, not intended to emulate different MATLAB releases.

- Supported MATLAB-language programs should have consistent numeric values, classes, shapes, and indexing results across modes.
- `matlab` mode excludes RunMat-only language features where accepting them would contradict the mode's purpose and controls MATLAB-style error identifiers where implemented.
- `strict` mode controls permissive syntax, including command-style calls. It does not select historical numeric semantics.
- `runmat` mode may expose deliberate extensions, subject to the extension rules below.

Release-specific runtime modes should not be introduced without a separate design review. They would multiply the semantic and testing surface and are not part of the current compatibility strategy.

## RunMat extensions

RunMat extends the MATLAB language with intentional language features that are not part of MathWork's MATLAB. Language extensions are designed to be a superset of MATLAB semantics, and are designed to not conflict with existing MATLAB code. Language extensions can be disabled with the compatability configuration flag described in the [Configuration Reference](/docs/runtime/getting-started/config). An extension must be classified before it becomes part of supported behavior.

| Classification | Meaning | Policy |
| --- | --- | --- |
| Safe extension | Adds capability without changing a program accepted by the semantic target | May be available in `runmat` mode and documented as an extension |
| Mode-gated extension | Accepting it conflicts with documented target behavior | May be considered for `runmat` mode; must not silently alter `matlab` mode |
| Incompatible divergence | Changes the result of a program accepted by the target | Do not introduce without a separate compatibility decision |

The existence of a useful internal representation or implementation path does not by itself justify exposing a new language behavior. Extensions must be intentional, documented, and tested.

Each mode-gated builtin signature or option must register a stable extension identifier, required compatibility mode, description, and error identifier in builtin metadata, and its implementation must enforce that same declaration through the shared runtime compatibility guard. This keeps documentation, tooling, and execution policy queryable from one registration record while allowing argument-dependent extension forms within an otherwise MATLAB-compatible builtin.

The `data.*` namespace is a RunMat persistence extension rather than a claim about MATLAB's numeric builtin surface. `data.create` accepts all eight integer dtype names and typed integer schema dimensions through exact host-side parsing and checked element-count multiplication; the remaining path lifecycle calls accept textual paths and formats only, even though their opaque filesystem operations preserve stored integer payloads. The unqualified `commit(tx, options)` helper is defined only for RunMat `DataTransaction` objects; unrelated object-specific `commit` methods remain separate compatibility surfaces.

Typed sparse integer storage is one mode-gated extension. MATLAB-compatible modes accept only documented `double`, `single`, and `logical` sparse payloads and reject construction, conversion, restoration, indexed access or assignment, and operation results that would expose sparse integer storage; `runmat` mode may preserve exact signed or unsigned sparse integer payloads. Sparse values remain host-resident in every mode because the current acceleration interface exposes dense tensor handles rather than native sparse device storage.

The legacy NaN-aware Statistics and Machine Learning Toolbox reductions (`nanmean`, `nansum`, `nanmin`, `nanmax`, `nanmedian`, `nanstd`, and `nanvar`) are not unconditional aliases for their modern replacements because their documented call forms and accepted classes differ. MATLAB-compatible modes retain the documented floating-input surface; typed-integer data or controls accepted through modern RunMat reduction machinery are individually registered and mode-gated extensions, while typed-integer data remains rejected for `nanstd` and `nanvar`. Compatibility checks inspect resident integer handle metadata before provider dispatch and do not gather device data merely to classify the call.

Canonical reductions retain their documented per-form integer contracts rather than applying a blanket numeric rule: `sum` and `prod` return double by default and preserve class with saturating `"native"` arithmetic; `median`, `min`, `max`, and both `bounds` outputs preserve integer class; and `std` and `var` reject integer data in every mode. The documented `std` and `var` data and weight domains are floating, so RunMat's useful typed-integer normalization and dimension controls are registered mode-gated extensions rather than silently widening the MATLAB-compatible surface.

`accumarray` treats positive integer subscripts and explicit positive sizes as exact structural controls across all eight integer classes. Integer data reaches an explicit group function as a native-class column vector, and the output plus any fill value follow that function's scalar result class; the default sum instead follows the documented double-output integer reduction rule. Sparse output remains double-only for data, fill, and group results, and interactive GPU-array execution rejects integer data and fill values before provider dispatch.

The partial-order reducers `maxk` and `mink` accept every integer class for observations and integer-scalar `k` and dimension controls, preserve the observation class in selected values, and return double indices while retaining stable source order for equal values. Real `ComparisonMethod="abs"` ties follow phase order, so positive real values precede negative real values in ascending order and the order reverses for descending selection. Interactive GPU arrays are not part of the documented surface used for this decision; RunMat therefore gates resident inputs as name-specific extensions, gathers through the owning provider, preserves exact integer and logical storage during selection, and restores both values and indices to that provider.

The ordering pair `sort` and `issorted` accepts every integer class for data and positive integer-scalar dimensions. `sort` preserves input class and stable source order while returning optional double indices; `issorted` compares integer storage exactly and returns scalar logical. Absolute-value and default complex ties use phase on the documented interval, and missing placement is explicit. `sort` fully supports resident GPU input and restores sorted values plus indices to the owning provider after an exact typed fallback when a native hook is unsuitable. Documented resident `issorted` is limited to vector input and `MissingPlacement="auto"`; RunMat's supported nonvector and explicit-placement resident forms are separate mode-gated extensions checked before gather.

`sortrows` accepts every integer class for matrix data and nonzero integer column selectors. Sorted values preserve exact input class, size, and stable equal-row order; optional indices are one-based double. Scalar or per-column direction lists override selector signs, and equal absolute magnitudes use phase order. Interactive GPU input follows the same all-class contract: compatible plain-real calls may use the owning provider's row-sort hook, while integer, logical, complex, and unsupported option forms use typed host fallback and restore every requested output to that provider.

`issortedrows` accepts every integer class for matrix data and nonzero integer column selectors, compares values exactly, and returns scalar logical. Ascending, descending, monotonic, strict, and per-column direction forms share the row-order contract with `sortrows`; strict forms reject duplicate selected row keys and missing values. MATLAB R2026a does not document interactive GPU-array execution for this predicate, so resident input is a mode-gated RunMat extension that gathers authoritative typed storage before evaluation.

`unique` accepts every integer class and preserves the input class for its value output while returning one-based double index outputs; element and row comparisons remain exact. Current missing-value semantics treat each missing instance as distinct by default, with `TreatMissingAsDistinct=false` selecting collapsed missing values. Interactive GPU input supports integer classes through 32 bits, rejects resident 64-bit integers and the documented unsupported combination of explicit set-order plus occurrence options before gather, and restores every requested output to the input handle's owning provider after typed fallback. `argsort` is a RunMat alias over `sort` and inherits its integer data, dimension, ordering, and provider contract while exposing only permutation indices.

The binary set functions `ismember`, `intersect`, `union`, `setdiff`, and `setxor` accept every integer class, require unlike nondouble numeric inputs to share a class, and retain the documented double cross-class exception. Value outputs preserve the applicable nondouble integer class while membership masks are logical and location/index outputs are double; element and row comparisons remain exact. Interactive GPU input supports integer classes through 32 bits, rejects resident 64-bit integers before gather, and restores every public output to the first resident input's owning provider after typed fallback.

`ismembertol` is a distinct floating-tolerance API rather than an approximate form of exact set membership. Its documented host data, tolerance, and `DataScale` classes are single and double, while documented interactive GPU data additionally includes integer classes through 32 bits and excludes 64-bit integers, `ByRows`, and `OutputAllIndices`. RunMat independently mode-gates host integer/logical data, typed integer/logical tolerance controls, resident 64-bit integers, and the restricted resident options before typed gather. Integer extension data retains authoritative storage until one explicit double tolerance boundary; ordinary resident logical and double-index outputs are restored to the owning provider, while the extended all-indices cell result remains host materialized.

`abs` accepts all eight real integer classes, preserves input size and class, leaves unsigned values unchanged, and applies saturating negation to signed values so the unrepresentable magnitude of `intmin(class)` becomes `intmax(class)`. Documented resident integer input uses exact typed fallback when a native hook is unavailable and restores the result to the input handle's owning provider. Sparse single and double inputs preserve CSC storage; exact sparse integer input remains the existing mode-gated RunMat extension. Logical and character inputs supported by RunMat are independently registered extensions because they are outside the R2026a input datatype list used for this decision.

The inverse-trigonometric cohort `acos`, `acosh`, `asin`, `asinh`, `atan`, and `atanh` documents single/double real or complex data plus table/timetable overloads, not typed-integer, logical, or character arrays. RunMat preserves native single/complex-single storage for the documented dense floating forms and retains all-eight-class real integer, logical, and character inputs as independently gated RunMat-only extensions; admitted nonfloating values preserve shape and enter one explicit binary64 computation boundary, including the documented possibility of complex-double output for the four domain-promoting functions. Resident integer/logical extension inputs gather from authoritative typed storage and restore the result to the owning provider. Public GPU notes for `acos`, `acosh`, `asin`, and `atanh` require explicitly complex input when output can be complex, so real resident input that crosses the complex domain is a separate RunMat-only extension; `atan(X,"like",P)` is likewise an independently gated RunMat output-template extension. Every name rejects more than one output, while the documented table and timetable overloads remain unimplemented feature gaps rather than integer compatibility forms.

`atan2` documents compatible-size real single/double inputs, not typed-integer, logical, character, or complex arrays. RunMat preserves the documented floating class rule: double inputs return double, single inputs return single, and mixed single/double operands compute in binary64 before the result is cast to single. All-eight-class integer inputs, logical inputs, and character inputs are independently gated RunMat-only extensions; authoritative integer storage crosses one explicit binary64 boundary only after compatible-size expansion. Resident fallback restores results to the first resident input's owning provider. Host, supplied provider, and fused execution all implement MATLAB's deliberate signed-zero exception: a mathematically zero numerator with a negative-zero denominator returns positive zero, while `atan2(-0,+0)` remains negative zero. More than one output is rejected, and table/timetable overloads remain an explicit feature gap.

`audioread` treats integer-class behavior as a file-decoding output contract rather than an integer-input overload. With `"native"`, documented integer-coded audio maps to `uint8` for 8-bit unsigned PCM, `int16` for 16-bit signed PCM, and `int32` for left-aligned 24-bit or ordinary 32-bit signed PCM; supported WAV/RF64 decoding writes those classes directly into authoritative storage and returns sample rate as double. The optional one-based inclusive sample range is explicitly a two-element double vector, with `Inf` accepted only as its final “through end” endpoint, so typed-integer sample controls reject rather than becoming an extension. The public API has no interactive GPU-array surface, and resident arguments reject before provider access. Additional documented container and codec support remains an implementation-coverage gap, not a different integer semantic.

`axes` has no integer-class output: it creates or selects an opaque graphics object. Its documented numeric ruler, aspect-ratio, layout, font-size, and tick-label-rotation property values accept all eight integer classes where RunMat exposes those properties. Authoritative typed storage is retained through vector shape and value validation, then crosses one explicit conversion into host `f64` graphics state; property queries therefore return double graphics values rather than preserving the input integer class. Resident property values reject before provider access because axes construction is a host graphics-state operation with no interactive GPU-array surface. Parent/current axes objects remain opaque handles, and RunMat's numeric handle encoding is not classified as integer data.

`axis` accepts all eight integer classes for documented four-, six-, and eight-element limit vectors and for the documented scalar numeric visibility controls zero and one. Authoritative integer storage is validated before one explicit conversion into host `f64` graphics state; limit queries return double vectors, and the eight-element setter also updates color limits while the query remains a four- or six-element spatial-limit vector. Logical visibility remains logical control input. Resident limits and visibility controls reject before provider access because axis configuration is a host graphics-state operation with no interactive GPU-array surface. Axes handles are opaque graphics objects rather than integer data. RunMat's remaining multi-argument target-setting and style-mode coverage is tracked as general graphics compatibility work rather than as a different integer semantic.

`bagOfNgrams` accepts all eight integer classes for documented nonnegative count matrices and positive scalar or vector `NgramLengths`. Counts remain authoritative through exact sign/integrality validation and n-gram column filtering before one deliberate conversion into the model's double `Counts` property; lengths convert exactly into bounded host indices before returning as double object metadata. The returned bag is an opaque text-model object rather than integer data. Resident counts and lengths reject before provider access because model construction has no documented interactive GPU-array surface. RunMat's current dense rather than sparse `Counts` storage is tracked as general Text Analytics compatibility work rather than as a different integer semantic.

`bagOfWords` accepts all eight integer classes for documented nonnegative count matrices. Counts remain authoritative through exact sign/integrality validation and vocabulary-column filtering before one deliberate conversion into the model's double `Counts` property. The returned bag is an opaque text-model object rather than integer data. Resident inputs reject before provider access because model construction has no documented interactive GPU-array surface. RunMat's current dense rather than sparse `Counts` storage is tracked as general Text Analytics compatibility work rather than as a different integer semantic.

`bandwidth` documents full or sparse single/double matrices, including complex and GPU input, and returns separate double lower/upper scalar outputs. All eight real and paired complex-integer classes are useful RunMat-only structural extensions, independently gated from the logical extension before host or provider dispatch. Host integer storage is scanned exactly for nonzero structure; resident integer/logical inputs gather exactly before the floating-only provider hook and return host double metadata. RunMat's missing sparse input implementation remains a general linear-algebra compatibility gap rather than a different integer semantic.

`bar` independently accepts all eight integer classes for X and Y data, the positional width scalar, and the `LineWidth` scalar. X remains authoritative through category-count and exact uniqueness validation, including wide `int64` and `uint64` labels, before the deliberate client graphics conversion; host Y and style controls cross one explicit floating graphics boundary. Floating gpuArray Y may use the shared WGPU geometry path, while resident integer Y gathers exactly before conversion so native integer buffers are never interpreted by a floating shader. Matrix Y returns one opaque Bar handle per series, and the documented default width is 0.8. RunMat's missing table overload and incomplete Bar property surface, including `BaseValue`, remain general graphics compatibility gaps rather than different integer semantics.

`barh` independently applies the same all-eight-class contract to horizontal charts: X and Y data, the positional thickness scalar, and the `LineWidth` scalar accept every integer class. Exact X category labels and uniqueness remain authoritative through validation, integer Y crosses only at the deliberate client graphics boundary, resident integer Y gathers before the floating WGPU geometry path, and matrix Y returns one opaque Bar handle per series. Its documented default thickness is 0.8; the missing table overload and incomplete shared Bar property surface, including `BaseValue`, remain general graphics compatibility gaps rather than different integer semantics.

`binocdf` documents single/double X, trial-count, and probability inputs, scalar expansion, single/double output, direct upper-tail computation, and full interactive GPU-array support. RunMat preserves native single-tensor output and resident ownership through an owning-provider gather/re-upload fallback. Typed-integer X, trial-count, and probability inputs are independent all-eight-class RunMat-only extensions, as are logical numeric inputs; each rejects before resident provider access in MATLAB-compatible mode. Admitted typed integers remain authoritative until an explicit binary64 distribution boundary and reject if an integer is not exactly representable there, preventing silent rounding of wide `int64` or `uint64` values. The runtime-wide scalar-single representation gap remains tracked separately from `binocdf` integer semantics.

`cdf` documents single/double evaluation points and named-distribution parameters, common-size array evaluation with scalar expansion, a numerically direct `"upper"` tail, and full GPU-array support. RunMat implements those public behaviors for its currently supported fitted and named distribution families, preserves native single-tensor output, and restores resident fallback output to the first input provider. Typed-integer evaluation points and typed-integer named parameters are separate all-eight-class RunMat-only extensions, and logical numeric inputs are a third extension; all reject from resident dtype metadata before provider access in MATLAB-compatible mode. Admitted typed integers remain authoritative through broadcasting and must be exactly representable at the deliberate binary64 distribution boundary, so wide `int64` and `uint64` values cannot be silently rounded. The smaller set of distribution families currently implemented by RunMat remains a general coverage gap rather than an integer-semantics divergence.

Current public [`cdfplot`](https://www.mathworks.com/help/stats/cdfplot.html) documentation accepts only single- or double-precision numeric vectors, creates the empirical CDF in the current or supplied axes, returns a host chart-line handle, and optionally returns host summary statistics; it does not document interactive GPU-array input. RunMat preserves dense typed-integer, dense logical, and resident sample data as three independently gated extensions. Every integer class remains authoritative through admission and provider gather, then values must fit the exact binary64 integer range before the single deliberate statistics-and-client-graphics boundary; a wide `int64` or `uint64` therefore rejects instead of silently collapsing adjacent observations. Resident inputs render through owning-provider host fallback and return the same host handle-plus-structure contract rather than implying a device-resident graphics result. Sparse numeric vectors remain a general input-surface gap rather than an integer-storage exception.

Current public [`ceil`](https://www.mathworks.com/help/matlab/ref/double.ceil.html) documentation exposes one numeric form, `Y = ceil(X)`, accepts single, double, every real integer class, char, logical, complex, tables, and timetables, and fully supports GPU arrays. RunMat treats every real integer input as an exact shape- and class-preserving identity operation: host and table/timetable variables retain authoritative native storage, while resident input returns the original owning-provider handle without invoking a floating shader or transfer. Logical and char inputs deliberately return double, native real and complex single remain single, and floating or logical provider fallback re-uploads to preserve residency. Typed complex-integer arithmetic remains rejected under the shared MATLAB-compatible rule. Duration overloads and portions of general table/static-type fidelity remain broader runtime surface work; decimal-digit, significant-digit, and `'like'` forms are not current `ceil` syntax and are not advertised.

Current public [`cell`](https://www.mathworks.com/help/matlab/ref/cell.html) documentation accepts square, variadic-dimension, and row-size-vector controls in single, double, or every integer class; signed negative dimensions are treated as zero, trailing singleton dimensions after dimension two are ignored, and every allocated cell contains a `0×0` double array. RunMat decodes all eight integer classes from authoritative storage without binary64 conversion, clamps signed negatives before checked host allocation, rejects logical and column-vector controls, and normalizes trailing singleton dimensions. The documented constructor has no interactive gpuArray or `'like'` surface: resident size controls and prototype-driven `'like'` contents are independently registered RunMat extensions that reject before provider access in MATLAB-compatible mode. The pre-existing nonconflicting no-argument `cell()` shorthand remains accepted without being speculatively classified from documentation silence. Java, .NET, and Python object conversion remains a foreign-runtime interoperability gap rather than an integer-storage distinction.

The text/introspection/display cohort keeps integer behavior at explicit metadata, passthrough, structural-control, or rendering boundaries. Public [`class`](https://www.mathworks.com/help/matlab/ref/class.html) reports the exact host integer class while a resident value reports the `gpuArray` container without provider access; [`convertCharsToStrings`](https://www.mathworks.com/help/matlab/ref/convertcharstostrings.html), [`convertStringsToChars`](https://www.mathworks.com/help/matlab/ref/convertstringstochars.html), and [`convertContainedStringsToChars`](https://www.mathworks.com/help/matlab/ref/convertcontainedstringstochars.html) return every non-target integer value unaltered, including nested and resident values, without gather or floating materialization, while top-level and contained target strings convert and empty or missing strings become `0×0` character arrays. Public [`dbstack`](https://www.mathworks.com/help/matlab/ref/dbstack.html) accepts all eight integer classes as an exact nonnegative scalar skip count but retains host debugger metadata output classes; until first-class structure arrays land, its documented `m×1` structure array is represented explicitly as an `m×1` cell column of scalar three-field structures rather than being silently described as identical. [`disp`](https://www.mathworks.com/help/matlab/ref/disp.html) and `display` render exact integer decimal values through host formatting, using typed gather fallback for resident arrays, and reject requested outputs. [`clearCache`](https://www.mathworks.com/help/matlab/ref/matlab.lang.memoizedfunction.clearcache.html), [`contains`](https://www.mathworks.com/help/matlab/ref/string.contains.html), and [`deblank`](https://www.mathworks.com/help/matlab/ref/deblank.html) have no documented typed-integer data surface; `clearCache` and `deblank` are therefore audited integer-inapplicable, while `contains` retains its prior positional, scalar numeric, and textual `IgnoreCase` conveniences only behind named RunMat-mode extension gates and requires the documented logical name-value form in MATLAB-compatible mode. Numeric resident inputs to text-only APIs reject before provider access.

`binornd` documents positive integer-valued single/double trial counts, single/double probabilities, integer-valued single/double size controls, scalar expansion, single/double output, nonpositive dimensions as empty results, and full interactive GPU-array support. RunMat preserves native single-tensor output and resident ownership through an owning-provider gather/re-upload fallback. Typed-integer trial counts, probabilities, and size controls are independent all-eight-class RunMat-only extensions, as are logical numeric inputs; each rejects before resident provider access in MATLAB-compatible mode. Trial counts and probabilities remain authoritative until an explicit binary64 sampling boundary and reject when an integer is not exactly representable there, while typed sizes are parsed exactly as structural controls without a floating compatibility mirror. The runtime-wide scalar-single representation gap remains tracked separately from `binornd` integer semantics.

Current public [`binscatter`](https://www.mathworks.com/help/matlab/ref/binscatter.html) and [`Binscatter` property](https://www.mathworks.com/help/matlab/ref/matlab.graphics.chart.primitive.binscatter-properties.html) documentation explicitly admits all eight integer classes for X/Y vector data, scalar or two-element `N`/`NumBins`, and two-element `XLimits`/`YLimits`; numeric table-variable selectors and numeric zero-or-one `ShowEmptyBins` are also documented. RunMat preserves integer X/Y and explicit integer limit tensors in chart state, validates vector shape and increasing limits before conversion, and computes same-axis integer bin membership with exact `i128` rational arithmetic across the full built-in integer range. `Values` and rendered bin edges deliberately enter the documented floating chart domain. Resident GPU-array input is not part of the documented extended-capability surface and is therefore a gated RunMat-only gather extension; MATLAB-compatible mode rejects it before provider access. Numeric scalar table selectors remain exact structural indices, while the broader R2026a pattern/logical/`vartype` selector set, datetime/duration data, tall arrays, and interactive rebinning remain general chart-surface gaps rather than integer-storage exceptions.

Current public [`bitand`](https://www.mathworks.com/help/matlab/ref/bitand.html) documentation accepts logical, double, and all eight built-in integer classes, requires the two operands to share a data type unless one is scalar double, preserves the common or nondouble integer output class, uses two's-complement signed representations, and applies compatible-size expansion. RunMat retains exact native integer storage across host and compiled dispatch, preserves logical output class, and applies `assumedtype` as an exact signed or unsigned interpretation width for double inputs while requiring it to match typed-integer operands. Public interactive GPU support is narrower: only `uint8`, `uint16`, and `uint32` arrays, optionally paired with scalar double, are admitted; 64-bit integers and `assumedtype` are excluded. RunMat implements that subset through exact owning-provider gather and typed re-upload, while single input, broader resident dtypes, and resident `assumedtype` calls are separately named RunMat-only extensions rejected before provider access in MATLAB-compatible mode. The documented .NET enumeration overload remains a platform-integration gap rather than an integer-storage exception.

Current public [`bitor`](https://www.mathworks.com/help/matlab/ref/bitor.html) documentation applies the same logical, double, and all-eight-integer host contract to bitwise OR: operands share a data type unless one is scalar double, nondouble output preserves class, signed values use two's-complement representation, compatible sizes expand, and `assumedtype` selects an exact signed or unsigned interpretation width for double input while matching typed-integer operands. RunMat preserves those host and compiled semantics without a floating mirror, including logical output class. The documented interactive GPU subset is likewise limited to `uint8`, `uint16`, and `uint32` arrays, optionally paired with scalar double, and excludes both 64-bit integers and `assumedtype`; RunMat gathers that subset exactly and restores typed output to the owning provider. Single input, broader resident dtypes, and resident `assumedtype` calls are three independently named RunMat-only extensions rejected before provider access in MATLAB-compatible mode. The public .NET enumeration overload remains a platform-integration gap rather than an integer-storage exception.

Current public [`bitshift`](https://www.mathworks.com/help/matlab/ref/bitshift.html) documentation accepts double and all eight integer classes independently for shifted values and integer-valued counts, requires the two inputs to be scalar or exactly the same size, and preserves the class of the shifted value. Positive shifts truncate overflowing high bits; negative shifts are arithmetic for signed values and logical for nonnegative values; counts at least the storage width exhaust the value accordingly. `assumedtype` selects the signed or unsigned interpretation width for double values and must match typed-integer values. Public interactive GPU support requires at least one integer-array input, forbids signed A and all 64-bit integer inputs, and excludes `assumedtype`. RunMat retains exact storage and restores documented GPU results to the owning provider, while single A, single k, logical A, logical k, broader resident combinations, and resident `assumedtype` calls are separately named RunMat-only extensions rejected before provider access in MATLAB-compatible mode.

Current public [`blackman`](https://www.mathworks.com/help/signal/ref/blackman.html) documentation accepts a nonnegative scalar length in single, double, or any of the eight integer classes, rounds noninteger floating lengths to the nearest integer, returns an L-by-1 double window by default, and lets `typeName` select single output after the optional symmetric/periodic sampling flag. Integer length is therefore an exact structural control, never an integer-output request. RunMat rejects reversed, duplicate, and excess option forms, gates its pre-existing scalar-logical length as a named RunMat-only extension, and uses the current R2026a `cospi` coefficient formulation across host and supported provider generation. The documented GPU capability is CUDA code generation rather than an interactive gpuArray input overload; RunMat's active-provider materialization is an internal acceleration choice for the newly created floating output.

Current public [`blanks`](https://www.mathworks.com/help/matlab/ref/blanks.html) documentation accepts an integer-valued scalar length in single, double, or any of the eight integer classes, treats negative lengths as zero, and returns a 1-by-n character row. Integer input is therefore an exact structural control and never an integer-output request. Public extended capabilities cover code generation and thread-based execution rather than interactive gpuArray input; RunMat gates its pre-existing resident-length gather behavior as a named RunMat-only extension before provider access.

Current public [`blkdiag`](https://www.mathworks.com/help/matlab/ref/blkdiag.html) documentation accepts rectangular matrix blocks, preserves sparse output whenever any public sparse input is present, and fully supports gpuArray input. Current public [`fft`](https://www.mathworks.com/help/matlab/ref/fft.html), [`fft2`](https://www.mathworks.com/help/matlab/ref/fft2.html), and [`fftn`](https://www.mathworks.com/help/matlab/ref/fftn.html) documentation accepts logical and integer transform data through 32-bit signed and unsigned classes, promotes that data into complex double output, and accepts integer-valued structural length and dimension controls. Current public [`fftshift`](https://www.mathworks.com/help/matlab/ref/fftshift.html) documentation accepts logical and all eight integer data classes, preserves class, complexity, value, and shape exactly, and accepts one positive integer-valued scalar dimension. ## Evidence policy

Compatibility decisions should be based on publicly available information and literature only. RunMat is a clean-room implementation of MATLAB compatable syntax, and as a result we do not rely on proprietary binaries, disassembly, or reverse engineering. Prefer evidence in this order:

1. Publically available explicit behavior documentation.
2. Publicly available release notes and documented version history.
3. Publicly available bug reports.
4. Publicly available Answers and authored explanatory material.
5. Independent technical sources that corroborate or clarify primary sources.
6. Community discussion as a signal about adoption or risk, not as sole authority for a semantic rule.

## Recording a semantic decision

A nontrivial decision should record enough information to reproduce and validate semantic behavior with tests, with notes within comments relevant:

| Field | Purpose |
| --- | --- |
| Target release | Release used as the primary reference |
| Surface | Operator, builtin, syntax, storage, or execution environment |
| Target behavior | Documented behavior for the target |
| Legacy behavior | Relevant earlier behavior, if different |
| Change release | Release in which public documentation reports a change |
| Conflict | Whether target and legacy behavior can coexist |
| Applicability | Core language, toolbox, accelerator, code generation, or other surface |
| Evidence | Direct public sources and whether the conclusion is explicit or inferred |
| RunMat policy | Behavior selected for RunMat |
| Tests | Conformance evidence in the repository |
| Remaining ambiguity | Unresolved or weakly supported details |

Compatibility gates apply to each broader input form independently. For example, row-wise character-matrix processing and recursive or non-cellstr text-cell processing are separate RunMat-only extensions for `eraseURLs` and `erasePunctuation`; enabling one form must not silently enable the other, and MATLAB-compatible mode rejects both with stable extension identifiers.
