# GPU Fast-Path Audit

This matrix tracks the eval-loop GPU residency pass for builtin work completed on the active branch. The rule for this audit is: if a builtin can reasonably preserve `gpuArray` residency, the implementation must route through the correct provider, plotting, or runtime layer. CPU-only compatibility is not considered complete for numeric array operations where a provider path is practical.

| Builtin / area | GPU applicability | Expected layer | Implementation evidence | Tests | Verdict |
| --- | --- | --- | --- | --- | --- |
| `pol2cart` coordinate transform | Yes: real elementwise transform with MATLAB implicit expansion and up to three outputs. | Runtime composes existing provider `unary_cos`, `unary_sin`, `elem_mul`, and `fill`; WGPU/simple providers own dispatch behavior. | `crates/runmat-runtime/src/builtins/math/trigonometry/pol2cart.rs` now keeps real GPU inputs resident; `crates/runmat-accelerate/src/simple_provider.rs` mirrors broadcasted numeric binary ops for `add`, `sub`, `mul`, `div`, and real `pow`. | `cargo test -p runmat-runtime pol2cart --lib` covers resident GPU outputs and mixed host/GPU cylindrical broadcasting. | Fixed in this audit lap. |
| Elementwise scalar math (`erf`, `gammaln`, `realsqrt`, ordinary trig/hyperbolic/log/sqrt helpers) | Yes for real dense arrays; complex support depends on hook semantics. | `runmat-accelerate-api` provider hooks, WGPU WGSL dispatch, simple-provider mirror, runtime fallback. | Existing provider hooks cover the main real unary paths. `realsqrt` additionally proves nonnegative inputs with provider `reduce_min` before `unary_sqrt`. | Existing focused builtin tests plus provider tests; verifier should sample CPU/GPU parity across the branch set. | Mostly covered; keep in verifier. |
| Exact pi trig (`sinpi`, `cospi`) | Conditionally. A naive `sin(x*pi)` / `cos(x*pi)` rewrite is not acceptable because exact integer and half-integer behavior is part of the contract. | Future dedicated provider hooks/kernels if implemented. Runtime host path is correct today. | Current GPU specs intentionally mark gather behavior and explain exactness constraints. | Existing exactness tests cover scalar/tensor/complex behavior. | Not counted as a missing fast path until exact provider kernels are designed. |
| Binary elementwise arithmetic used by compatibility helpers (`bsxfun`, mixed scalar ops, coordinate transforms) | Yes when operands are dense numeric/logical arrays with MATLAB broadcast-compatible shapes. | Provider binary hooks and simple-provider mirror; runtime should only gather when hooks are unavailable. | WGPU already supports broadcasted binary dispatch. This lap extends the simple provider's numeric binary hooks to the same broadcast contract. | `pol2cart` mixed GPU test exercises `elem_mul` broadcast; verifier should add broader provider parity samples for add/sub/div/pow. | Improved; broader verifier remains. |
| Array creation and grid helpers (`zeros`/`ones`/`eye`/`rand*`/`linspace`/`meshgrid`/`ndgrid`) | Yes for dense numeric outputs, especially `like`/prototype forms and resident grid-vector inputs. | Provider constructors where available; runtime upload fallback only when provider lacks a hook or the axis class requires host materialization. | Constructor hooks exist for common creation paths. `ndgrid` now has a provider hook for resident real/logical GPU vector axes, with simple-provider coverage and WGPU dispatch plumbing. | Existing constructor tests plus `ndgrid_gpu_inputs_use_provider_resident_outputs`; verifier should inspect WGPU residency behavior. | Covered for resident real/logical axes; complex/provider-missing fallback remains host materialized. |
| Plotting geometry builtins (`line`, `bar*`, `quiver*`, `stem`, `contour*`, scatter-like helpers) | Yes when plot geometry can consume exported provider buffers; otherwise plotting is a sink. | `runmat-plot` shared GPU context/exported-buffer paths, not runtime god files. | Many plotting docs and implementations state direct GPU geometry paths or intentional gather boundaries. | Existing plot tests; verifier should audit representative direct paths. | Partially covered; verifier follow-up. |
| Statistics and ML numeric summaries (`cov`, `corrcoef`, `corrcov`/`cov2corr`, `gradient`, distribution helpers, moving stats, `mode`) | Mixed. Reductions and simple transforms are GPU-feasible; order/statistical control flow may be host-only unless dedicated kernels exist. | Provider reductions/scans/linalg hooks for feasible dense paths; runtime host fallback for unsupported algorithms. | `cov`/`corrcoef` have provider specs. `cov` now preserves residency for `rows='all'` weighted covariance when host weights can be temporarily uploaded or resident real gpuArray weights already live on the same provider; `omitrows`/`partialrows` remain host fallback. `corrcov`/`cov2corr` now route resident real gpuArray covariance matrices through `covariance_to_correlation`, with simple-provider and WGPU dispatch plus device-side validation flag readback. `mode` currently rejects GPU input and should be reviewed separately. | Existing focused stats tests plus `cargo test -p runmat-runtime cov --lib`, WGPU weighted `cov` coverage, `cargo test -p runmat-runtime covariance_conversion --lib`, and provider/WGPU `covariance_to_correlation` coverage. | Partially covered; verifier follow-up for remaining dense reductions/order stats. |
| Deep-learning runtime slices (`crossentropy`, `adamupdate`, training helpers) | Yes for tensor loss/optimizer updates, but requires dedicated provider kernels and residency-aware parameter-tree handling. | `runmat-accelerate` provider hooks plus runtime tree routing. | `adamupdate` preserves residency for plain real `gpuArray` parameter, gradient, and optimizer-state tensors through the `adam_update` provider hook. `crossentropy` preserves residency for plain real same-shape `gpuArray` prediction/target tensors through the `crossentropy_terms` provider hook; unreduced loss arrays remain resident and scalar reductions reduce on the provider before scalar readback. Weighted and masked `crossentropy` forms stay provider-side when host factors can be expanded to the prediction shape or resident real GPU factors are already prediction-sized; `WeightsFormat` remapping for resident GPU weights and mask-included GPU normalization still fall back to host semantics. GPU-backed `dlarray` metadata/autodiff support remains future work. | `cargo test -p runmat-runtime adamupdate --lib`, `cargo test -p runmat-runtime crossentropy --lib`, provider `adam_update`/`crossentropy_terms` coverage, and WGPU `adam_update_wgpu`/`crossentropy_wgpu` coverage. | Partially covered; core plain `gpuArray` optimizer/loss paths are fixed, broader training infrastructure remains queued. |
| Finance/vector formulas (`blsprice`; implied volatility) | `blsprice` is GPU-feasible as vectorized elementwise math; implied volatility is iterative host control flow unless a solver hook is added. | Provider custom hook for pricing; runtime host for solver. | `blsprice` now routes resident real gpuArray inputs through `ProviderBlackScholesPriceRequest`; simple provider and WGPU own the pricing dispatch, with temporary upload only for mixed host/GPU operands. | `cargo test -p runmat-runtime black_scholes --lib` covers CPU implicit expansion and resident GPU outputs; `cargo test -p runmat-accelerate black_scholes_price_expands_resident_inputs --lib` covers provider broadcast parity. | Covered for pricing; `blsimpv` intentionally remains host-side. |
| Sparse matrix compatibility | Not yet, until RunMat has GPU sparse storage semantics. | Future sparse provider/storage layer, not dense runtime shortcuts. | Sparse constructors/arithmetic remain host-resident or reject GPU sparse mixing. | Sparse tests. | Not in this fast-path pass. |
| IO, filesystem, datetime/duration, table/timetable, graph/digraph, object/type introspection, app/UI dialogs, Java/external integration | No meaningful device compute path for core semantics; inputs may be gathered only to inspect metadata or format values. | Runtime/IO/object/plot metadata layers. | Implementations are host metadata, parsing, file/network, or handle state. | Existing unit/docs coverage. | Not GPU-applicable. |
