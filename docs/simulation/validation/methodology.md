## What validation establishes

RunMat checks finite-element analysis at three levels: the mechanics of each formulation, numerical accuracy against physical references, and preservation of the result through the complete execution workflow.

A successful solve establishes that the assembled equations meet their numerical acceptance criteria. Confidence in a physical prediction also depends on the formulation, mesh, boundary conditions, and comparison quantities used for that problem.

## Formulation checks

Element tests check strain, stress, stiffness, integration, and load projection. Their acceptance criteria identify the element orders and material laws they cover.

## Physical references and refinement

Independent reference problems and mesh refinement check displacement, stress, reactions, and other physical quantities. Each assessment must identify its tested configuration, acceptance criteria, decision, and limits. A field plot alone does not establish convergence.

## Complete workflow checks

Execution checks cover authored studies, resource admission, original saved fields, and reopening results with their provenance. They establish that the workflow preserves the numerical answer within the assessed scope.

## Reading requirement evidence

The requirements in the [capability ledger](#status-and-the-capability-ledger) list every acceptance obligation and the execution envelopes it must hold in. Each supporting test declares, at the test, which obligation and envelopes it supports and what its assertions do and do not cover. The evidence catalog is generated by running those tests: for every requirement, obligation and envelope it reports PASS, PARTIAL, FAIL or OPEN with the test locator and its stated boundary. A cell is PASS only when every test that claims it passed in that run; OPEN means no test supports it yet.

The catalog is regenerated, never edited by hand: `evidence_report` in `crates/runmat-analysis/qualification` writes the evidence catalog at `docs/simulation/qualification/generated/evidence-catalog.md` (markdown and JSON, with one page per requirement) and the scope traceability table, which maps every claim in the ledger to the obligations that hold it to account. Each family page shows the counts for its requirements.

## Correctness layers

No single test validates a physics family. Confidence is earned per formulation and per intended use, in layers:

| Layer | Question | Evidence |
| --- | --- | --- |
| Input checking | Is the `.fea` source or model well formed? | `runmat check` diagnostics: syntax, types, units, region resolution, material coverage, family and procedure admission. |
| Contract correctness | Does the public operation behave as specified? | Versioned result envelopes, typed errors, payload snapshots, builtin tests. |
| Solver verification | Does the implementation solve the intended discrete problem? | Residual checks, deterministic replay, convergence diagnostics, execution-provider provenance. |
| Numerical verification | Does the discretization converge toward known answers? | Closed-form cases, manufactured solutions, patch tests, mesh and time-step convergence. |
| Physical validation | Does the model match trusted external behavior? | Published benchmarks, independent solver comparisons, measured references. |

Model checks run before any assembly. They reject non-finite or inadmissible material properties, duplicate materials, material gaps and overlaps, unresolved regions, wrong formulation roles, cross-geometry assignments, and mismatched signal, excitation, constraint, boundary and interface quantities. Invalid material data and invalid assignments carry distinct diagnostics, so a solver failure is never the way an input error is reported.

## Adding a validation case

1. State the engineering question, the physics family and the procedure.
2. Choose the reference: closed form, manufactured solution, patch test, published benchmark, independent solver, or measurement.
3. Record geometry, units, materials, loads, constraints, assumptions and the acceptance tolerance.
4. Add the study to the example package or the qualification harness.
5. Assert physical quantities (displacement, reaction, frequency, temperature, flux), not only the result shape.
6. Add a convergence sequence when the quantity depends on mesh density, time step, mode count or load increments.
7. Tag the test with the requirement obligation it supports, so the evidence catalog picks it up.
8. Add the case to the ledger: a `cases` entry with its write-up under `validation/cases/`, its references, receipts and tests, and its id in the `verification` list of each capability it covers. Regenerate the pages with `node scripts/docs/generate-pages.mjs`.

## Terms

| Term | Use for |
| --- | --- |
| Input checking | Syntax, types, units, regions, materials, loads and options in a `.fea` source, reported by `runmat check`. |
| Evidence | Diagnostics, provenance, receipts and test records attached to a result. |
| Verification | Showing the implementation solves the intended discrete equations correctly. |
| Validation | Showing the model matches known physical or trusted external behavior for a stated use. |

Never call a whole family "validated". Name the formulation, the procedure and the envelope (element order, mesh, execution provider) a case covers.

## Status and the capability ledger

What the current release runs, and what is planned, is recorded once: in the capability ledger, `docs/simulation/ledger.json`. Each row is a capability (a family and procedure, a load or constraint, an output, a language feature) with its status, the requirement ids it answers to, its verification cases and the docs pages that describe it. The compiler's table of family and procedure pairs is generated from the ledger, so `runmat check` and `runmat run` admit exactly what [Status](./status.md) lists, and the docs' "not yet in the current release" markers name ledger rows.

A status changes only in the same change that adds the implementation, the reference cases and tests that verify it, and the docs that describe it. Name the formulation, procedure and envelope a case covers; never mark a whole family validated.
