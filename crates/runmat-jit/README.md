# runmat-jit

`runmat-jit` owns native compilation policy, publication, execution hosts, runtime feedback, entry cells, invalidation, and executable-memory lifecycle. It consumes verified products from `runmat-native-codegen` and the runtime-owned native ABI. It does not lower MIR, define runtime value storage, own MATLAB semantics, or reconstruct bytecode control flow.

The generic host is split by responsibility: compilation retains executable memory, each invocation owns an opaque generation-checked value arena and ABI frame, callbacks contain panics at the C boundary, and semantic-site execution consumes the immutable Native IR payload through shared runtime operations. Rust `Value` layouts never enter generated code or the native ABI. Unsupported semantic cohorts fail explicitly; they are never replayed through the bytecode interpreter after native entry.

Native ABI schema 3 removed the obsolete required `slow_call` callback: generated code uses the typed semantic-site dispatcher, while the host table retains only implemented lifetime, safepoint, source, and site services. Schema 4 makes resume identity exact to function, block, position, phase, and ordinal. ABI version/layout fingerprints and native cache keys change with either contract, so stale native objects cannot be loaded against a different host table or resume layout.

Invocation lifecycle is separate from one generated-code entry. An invocation owns its value arena, locals, roots, arguments, result window, and exact resume state for its complete lifetime; short-lived C-compatible frame/call/vtable records borrow that stable state only while machine code is active. The arena is also a live RunMat GC root source: construction values remain scoped roots until transfer, every occupied generation-checked slot is traced throughout native execution and deoptimization, and teardown unregisters the scanner before releasing storage. Generated entry dispatch reads the validated resume block and can re-enter a verified block without replaying the function entry. Structured exception exits materialize Runtime's canonical `MException`, transfer exact edge locals to the innermost active catch, and resume at that verified catch block within the same invocation. Nested catches and `rethrow` retain outer handlers without replaying function entry or completed effects. Future creation and spawn use Runtime's execution handles and capture policy. Await publishes the exact post-await resume site and roots in the native exit, completes or polls the executor-owned work outside generated code, transfers the result or exception through its verified edge, and resumes the same invocation. No Rust future, `Value`, VM frame, or JIT object enters the native ABI.

Specialized regions consume the portable guard contracts emitted with Native IR. Runtime values are adapted back into dependency-neutral `ValueFact` constraints, including partial shapes and aggregate facts; runtime revisions and capability grants come from the invocation-owned guard environment. A failed guard is retired for that invocation and exits through the native deoptimization ABI with its exact MIR site, source span, live locals, operation operands, aliases, call counts, omitted-input state, and side-effect epoch. Generic-native continuation always remains available. Core selects interpreter continuation only when the VM compiler published the corresponding empty-stack bytecode boundary and no native-only loop, exception, mutation, or await state is active. Otherwise the request fails closed to generic-native continuation. Neither path restarts the function or replays a completed semantic site.

Operators, calls, aggregates, conditions, and MATLAB column iteration stay runtime-owned. The JIT adapters only materialize Native IR operands, preserve requested-output contracts, and select compiled edges. Loop snapshots are invocation-owned: an iterable is evaluated once, retained across compiled backedges, and retired on exhaustion or any edge leaving the natural loop body. Cancellation is checked at every generic semantic site, with exact frame roots, resume points, source spans, and side-effect epochs refreshed around host work.

Call adapters materialize ordinary and comma-list operands in source order, then use Runtime's shared argument-expansion service for cells, output lists, and overloaded object brace access. Static, dynamic, superclass-constructor, and superclass-method calls all enter Runtime's canonical dispatch services with the requested output contract. The VM consumes the same expansion service after decoding its operand stack; neither executor owns a second expansion algorithm.

Function entry and return use Runtime's shared ABI semantics as well. Native IR binds the dependency-neutral argument-validation/default vocabulary to exact native locals; the host projects those locals to fixed-input order, preserves omitted inputs as unassigned, materializes `varargin`, `nargin`, `nargout`, and an empty `varargout`, and delegates validation and output assembly to Runtime. Declared function outputs are read from exact ABI locals in the verified return frame; only synthetic MIR with no declared output ABI consumes the terminator's canonical return vector directly. The VM performs only the corresponding bytecode-slot projection. Lexically nested entry uses Runtime's binding-keyed call envelope to keep captures separate from ordinary arguments and return updated shared bindings. Direct nested calls apply those updates to the parent locals; bound and anonymous handles reuse the canonical `Value::Closure` capture-by-value representation.

Index and member adapters likewise consume runtime-owned selector plans, type-preserving reads/writes, object resolution, overload dispatch, and GC barriers. Nested assignments are reconstructed from the changed leaf back to one Native IR root local, and only that updated root is published into the next SSA state. Fixed multi-output indexing preserves discard and comma-list arity; unsupported selector forms fail at their semantic site rather than replaying the function through another executor.

Workspace adapters use the semantic local catalog retained in Native IR rather than VM frame slots. Global and persistent declarations load and synchronize session-owned values by canonical name on every root write, which preserves state across native invocations and across executor boundaries. Workspace-first static-property reads prefer the active workspace or matching named local before shared runtime class resolution. Workspace and environment markers emitted after runtime calls are committed as ordered effect sites but are not replayed, because the preceding call already performed the mutation.

Context-dependent indexing temporaries are retained as verified Native IR recipes and are not eagerly executed. At the actual index site, the host resolves scalar and range `end` expressions once against the base's linear or selected dimension, using Runtime's executor-neutral evaluator and callable path. This prevents placeholder arithmetic and avoids replaying calls or effects embedded in selector expressions; the same evaluator is used by the bytecode VM.

Core owns executor selection, semantic publication, and the exact immutable executable unit supplied to this host. The JIT retains stable entry cells separately from replaceable machine-code targets. Every target records exact program, builtin-catalog, and referenced session-function generations; dynamically resolved calls additionally depend on the session catalog. Repeated invocation of the same dependency snapshot reuses executable memory, an unrelated function definition leaves the target live, and a referenced redefinition retires the target before the replacement is published. Provider generations use the same dependency vocabulary but are attached only when a later specialized target actually depends on one, so the current provider-neutral generic tier is not recompiled unnecessarily.

Tier feedback and compilation policy are JIT-owned but session-scoped. Stable program/function/loop identities accumulate bounded invocation, backedge, representation-profile, failure, and timing observations; profile identities are hashes of the dependency-neutral `ValueFact` sequence and are checked before admission. Policy decisions are monotonic from interpretation through generic native code to guarded specialized versions, subject to explicit pending-compilation, retained-version, and executable-byte limits. Deterministic mode requests synchronous compilation for tests and reproducible execution; ordinary mode may request background work, but only the owning session may publish a completed target. Feedback snapshots encode counters as decimal strings so telemetry remains exact in JavaScript consumers. A failed specialization is quarantined without disabling its generic-native continuation.

A specialized product retains the exact admitted fact sequence and checks it before machine-code entry; the session also requires the current invocation digest to match before selecting that product. Specialized Cranelift code uses the speed optimization pipeline, while the generic product remains the unconditional continuation. Once a replacement has compiled successfully, publication may retire the oldest specialized products to satisfy per-entry version and session executable-byte limits, but it never retires the generic continuation or code retained by an active invocation.

Core's immutable-executable path applies that policy directly: cold calls use the canonical VM or semantic-function path, exact argument facts accumulate in the session, and hot generic compilation lowers and compiles an owned immutable input on a bounded background worker. The session continues interpreting while work is pending and publishes the completed target only after rechecking its dependency generations and executable-byte budget. Deterministic test mode performs the same lowering, compilation, admission, and publication sequence synchronously. Completed native invocations return saturating backedge counts keyed by exact loop-header `ProgramPointId`; Core records both the loop-specific site and its function aggregate in the same bounded session feedback authority.

When an exact loop site crosses the OSR threshold, Core may admit a matching specialized product through the same dependency, version, and executable-byte budgets and attach it to a later generic invocation. The generic host exits before selecting the loop's next column, materializes the verified loop-header frame, and re-enters the retained optimized entrypoint at that exact site. The invocation keeps both executable generations alive, preserves the runtime-owned iterator and all frame roots, and records one transfer for telemetry. Profile mismatch, unavailable background work, stale dependencies, or failed admission leave generic execution unchanged; OSR never recompiles inside a semantic callback, restarts the function, or replays a selected iteration.

Guarded specialized products may also derive bounded numeric-region plans from verified pure-region contracts and exact Native IR sites. The JIT owns plan derivation and callback skipping, but not a second arithmetic implementation: Runtime evaluates the admitted scalar/dense-double expression DAG, polls cancellation, and stages every computed result before publication. Unchanged live-ins retain their existing arena references; computed values are deduplicated and materialized only when an exit live-out or preserved Native IR consumer requires them. Each eligible invocation asks the session's shared placement authority to compare ordinary specialized execution with the vectorized CPU candidate, and the JIT contains no provider or GPU policy. Missing placement authority, unsupported values or shapes, resource rejection, or an adaptive decision for ordinary execution leaves the original specialized sites intact. A selected result is published atomically to its exact local and SSA bindings, then only the already-computed sites are skipped; exact point/phase/ordinal identities and invocation-local skip state allow the same region to execute correctly on every loop visit. Placement feedback records completed and failed attempts, while Core reports successful vectorized-region counts with the rest of its native execution telemetry.

HIR function ordinals remain dense and unit-local while lowering. At Core's publication boundary, one checked map moves local functions together across MIR, analysis, VM layout, bytecode registry, and the executable manifest into the session/program namespace. Session-published dependencies retain their distinct `ExternalFunction` identity and are not rewritten even when their original numeric ordinal matched a local function before publication. Runtime provides a focused external-function call port rather than collapsing both identities into the ordinary semantic-function callback. Nested functions from the unit therefore route through the same native executor, while genuine external calls execute from Core's retained session registry or delegate to an already installed external invoker. There is still no whole-function fallback or replay after native entry. Active invocations retain their published target through `Rc` ownership while invalidation removes it from the stable cell, so replacement cannot reclaim code that is still running.

Ordinary semantic callbacks remain deliberately synchronous and never start a nested futures executor. Each such runtime operation is polled once inside its `RuntimeContext`; an immediately ready result continues native execution, while an unexpected `Pending` result remains an explicit unsupported-site error. MIR `Future`, `Spawn`, and `Await` are the intentional exception: they use the invocation-owned continuation lifecycle, preserve exact program and runtime context, and resume without replaying completed sites. The synchronous `invoke` API therefore remains valid only for programs that do not suspend; async consumers use `invoke_async`.

Host-native executable memory is unavailable in a web/WASM process. WASM consumers retain and verify the same portable executable and generic Native IR products; browser execution uses its platform executor rather than embedding a native Cranelift JIT.
